# Backend requirements for order verification

## Current behavior

The current backend stores an order with:

- Internal UUID.
- Creator user ID.
- Optional note.
- Status (`PENDING`, `APPROVED`, or `REJECTED`).
- Admin decision metadata and timestamps.

The backend correctly enforces:

- A CTV only sees their own orders.
- A Super Admin sees all orders.
- A CTV cannot exceed five concurrent pending orders.
- Only approval creates the +50 F customer reward and the +10 F direct-referrer reward.
- Rejection creates no point transaction.
- Redemption is unlocked after the user has earned a `CUSTOMER_REWARD`.

## Required data additions

To support real customer/payment verification, the backend should eventually persist:

### Customer

- `full_name`
- `phone`
- Optional date of birth and address
- Owning CTV
- Created/updated timestamps

### Order

- Internal UUID
- Public, unique order code
- Customer ID
- Creator CTV ID
- Payment reference
- Optional payment date and amount
- Optional proof attachment reference
- Status
- Request-for-information/rejection reason
- Admin decision metadata
- Created/updated/submitted timestamps

No activation-code field is required.

## Recommended statuses

| Status | CTV can edit | Points generated |
| --- | --- | --- |
| `DRAFT` | Yes | No |
| `PENDING` | No | No |
| `NEEDS_INFO` | Yes | No |
| `REJECTED` | No | No |
| `APPROVED` | No | Yes |

An order should be immutable after approval. Locking an order does not itself generate
points; the guarded `PENDING` to `APPROVED` decision remains the point-triggering event.

## Public order-code recommendation

The public order code should be generated by the backend, not supplied by the browser.
A temporary format may be:

```text
XKLD-202607-AB3921
```

The database must enforce uniqueness. The internal UUID should remain the primary key.

## Payment proof options

The first implementation can require a payment reference and keep proof images optional.
This avoids introducing file storage before it is needed.

If proof uploads become mandatory, the backend will also need:

- Authorized upload endpoints.
- Object storage such as R2.
- File-size and MIME-type restrictions.
- Private access or signed download URLs.
- Audit and retention rules for personal/payment information.

## API additions

The future API should cover:

- Create customer.
- Create draft order.
- Update a draft or `NEEDS_INFO` order.
- Submit an order for review.
- View order details and decision history.
- Admin request for additional information with a required reason.
- Admin approve/reject.

All ownership and role checks must be enforced in backend queries, not only hidden in the UI.

## Redemption behavior to preserve

The current redemption logic remains the source of truth:

- The user must previously have earned a customer reward.
- Admin may deduct a positive integer from F, G, or both.
- Each targeted wallet must have sufficient balance.
- F is never automatically reset; it only decreases by redemption entries.
- G follows the rolling three-month maintenance/reset rules.
- Ledger history is immutable.

The current backend has no pending reward-payment workflow. The frontend therefore treats
Zalo and external transfer as operational guidance; the Admin records redemption after the
external payment is completed.
